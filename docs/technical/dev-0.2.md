## 2. 系统职责与状态流

本轮沿用 Python 标准库规则引擎、本地 HTTP 服务和原生浏览器界面的结构。一次操作由浏览器发出意图，Python 验证并修改牌局，再把最终状态交还前端显示。

当前保留的职责入口为：

| 位置 | 职责 |
|---|---|
| [engine.py](../../tile_explorer/engine.py) | 九关参数、牌数据、遮挡、取牌、三消、工具、通关路线 |
| [content.py](../../tile_explorer/content.py) | 三座城市与每城三条知识资料 |
| [server.py](../../tile_explorer/server.py) | 会话、操作路由、完成记录的读取与保存 |
| [app.js](../../web/app.js) | 操作请求、主题展示、棋盘与暂存槽渲染、工具激活状态 |
| [index.html](../../web/index.html)、[style.css](../../web/style.css) | 页面结构、三个工具入口及响应式样式 |

当前接口以 `GET /api/state` 获取状态，以 `POST /api/action` 提交操作；`action` 为 `pick`、`magic`、`undo`、`shuffle`、`level`、`restart` 或 `next`。规则校验由服务端完成，前端按钮状态不能代替校验。

## 3. 三城九关的数据组织

### 3.1 关卡参数

历史日志明确记录以下九关规模；当前 `engine.py` 以 `COUNTS`、`KINDS`、`LAYERS` 三组常量保留相同配置：

| 关卡 | 城市 | 牌数 | 图案种类 | 层数 |
|---:|---|---:|---:|---:|
| 1 | 巴黎 | 12 | 3 | 1 |
| 2 | 巴黎 | 18 | 4 | 2 |
| 3 | 巴黎 | 24 | 5 | 2 |
| 4 | 京都 | 27 | 6 | 3 |
| 5 | 京都 | 30 | 7 | 3 |
| 6 | 京都 | 33 | 8 | 3 |
| 7 | 纽约 | 36 | 9 | 3 |
| 8 | 纽约 | 42 | 10 | 4 |
| 9 | 纽约 | 48 | 12 | 4 |

当前按 `(number - 1) // 3` 选择城市，按 `(number - 1) % 3` 选择城内关卡与知识条目。关卡边界限定为整数 1–9；布尔值、浮点数和字符串等不作为合法关卡编号。

图案库共 18 种，水果、交通、宠物各六种。当前 `SYMBOLS` 为每个图案提供名称、颜色、稳定 `code` 与分类，牌中的 `kind` 索引该图案库；每关取其中部分图案，各类型总数为三的倍数。

### 3.2 可通关布局的构造

历史日志记载四套种子、九关共 36 条完整路线回放通过。当前继承实现的构造方式如下：

1. 根据关卡牌量与层数建立位置，给每张牌分配唯一 ID 和 `x/y/z`。
2. 计算遮挡关系，反复从当前没有上层阻挡的牌中选择一张，得到合法移除顺序。
3. 建立每类数量为三的倍数的图案池。
4. `safe_kind_order()` 按暂存槽占位约束生成图案序列，再依移除顺序分配图案。
5. 将该移除顺序保存在 `Level.solution`，用实际规则回放确认能够清空。

当前额外使用 `PRESSURES = (3, 3, 4, 4, 4, 5, 5, 6, 6)` 控制构造路径的槽位占用压力。此数值来自当前源码，历史日志未逐项记载，不能视为当时参数快照。

这种方法保证初始布局及重排后的布局至少存在一条通关路径。玩家偏离路径后可能形成死局；内部路线不等于任意后续操作都有解。当前 `certificate` 只在玩家沿记录路径取牌时继续保留，偏离、撤回后会失效。

## 4. 取牌、七格槽与三消顺序

当前保留的数据模型把一张牌表示为不可变的 `Tile(id, kind, x, y, z)`。棋盘按 ID 保存 `Tile`，暂存槽保存牌对象，并单独保存实际入槽顺序。

遮挡使用 2 × 2 世界单位的矩形：只有更高层存活牌与本牌存在正面积交集才算阻挡，边缘相接和同层牌不算。普通取牌拒绝仍被阻挡的牌；底牌可见只帮助观察，不自动赋予取牌资格。

当前 `pick()` 的关键顺序为：

1. 校验牌局状态、牌 ID 及是否允许穿透遮挡。
2. 从棋盘移除目标牌，插入槽中同类牌之后；没有同类则放末尾。
3. 记录真实入槽顺序并更新步数、峰值槽位数。
4. 同类达到三张时立即移除该组三张，并清理它们的入槽顺序记录。
5. 棋盘和槽同时为空则判胜；否则才检查槽是否达到七格并判负。

因此第七张刚好组成三张时会先消除，可以继续游戏。相同牌自动靠拢只改变显示顺序，不能用槽的最后一格判断“最近加入的牌”。

当前得分逻辑在三消时累计组合得分，通关时追加通关分。撤回不回退这些已结算得分；历史日志明确记录了这一语义，但没有给出当时各项分值，因此不在此补造历史数值。

## 5. 三个工具如何实现

### 5.1 撤回一张

历史变更是从整局历史回滚改为“取回槽中最近加入、仍未消除的一张”。当前实现使用独立 `tray_order` 记录先后，倒序查找还存在于槽中的 ID，将其原 `Tile` 放回棋盘。

由于保留了原 `x/y/z`，撤回可回到原位置。已消除的 ID 会同时从槽和顺序表删除，所以不能恢复整组三张，也不会倒退消除次数和得分。满槽失败后，只要槽内有牌，撤回会把状态恢复为 `playing`；空槽时拒绝操作。

### 5.2 魔法笔

前端维护一次性 `magicArmed` 激活状态。点亮后点击被压牌，发送 `magic` 和牌 ID；当前服务端通过 `pick(..., penetrate=True)` 复用普通入槽、三消和胜负结算。

魔法笔只接受当前仍被遮挡的牌；未被遮挡的牌按普通取牌处理。成功使用后前端关闭激活状态，也允许再次点击按钮或按 Escape 取消。只要牌尚未消除，魔法取出的牌也能撤回原位置。

### 5.3 整体重排

重排的输入为“棋盘存活牌 + 槽内未消除牌”，不能只洗棋盘。当前实现先合并所有剩余牌，再生成位置、合法移除顺序和受控的图案序列；完成后清空槽和入槽顺序表，回到 `playing`。

需要守恒的是剩余牌数、ID 集合和各图案数量。当前实现为确保新路径可解，会重新把图案分配给 ID，因此不保证某个 ID 在重排后仍对应原来的 `kind`。已消除的牌不会加入重排。通关后禁止重排，满槽失败后允许重排救援。

三个工具均无能量要求和次数上限；使用统计用于当前成绩与星级记录，不构成消耗门槛。

## 7. 城市内容、选关与存档

`content.py` 当前按城市组织标题、颜色与三条 `facts`；每条包含知识标题、正文、来源标题及 HTTPS 链接。前端根据当前城内关序选取一条，切关时同步背景、城市名、章节序号和知识内容。来源是内容资料，不是运行时抓取任务，游玩中不联网请求 AI。

选关可直接重建任意一关，也承担重开当前关的作用。`next` 要求当前已通关，且第九关结束后拒绝进入第十关。底栏仅保留撤回、魔法笔、整体重排，旧提示、回声模式、能量和额外重开入口移除。

本轮将完成记录隔离至 `.local/travel-progress-v2.json`，避免旧版成绩混入九关版本。当前保留的存档结构为：

```json
{
  "completed": {
    "1": { "stars": 3, "best_score": 1020 }
  }
}
```

上例分值仅演示字段。当前记录按关号保存最高星数与最高分；先写临时文件再替换目标文件，并在写入失败时保留内存记录和告警。读档过滤损坏、类型错误和越界条目。上述字段及容错细节来自现存 `Progress`，没有独立历史快照可逐项核对。

进行中的牌局按浏览器 Cookie 会话隔离，保存在 Python 服务内存；同一会话刷新可继续，停止服务则结束牌局。完成记录在该本地服务内共享，不是账号数据或云存档，也不使用浏览器 localStorage 保存当前牌局。
