## 2. 运行结构与模块边界

项目使用 Python 3.10 及以上版本的标准库和原生浏览器 HTML、CSS、JavaScript，无需第三方运行依赖。Python 保存权威牌局、校验操作和结算胜负；浏览器提交操作意图，并根据完整状态重绘界面。

| 文件 | 职责 |

| [main.py](../../main.py) | 解析端口参数，启动本机服务，按需打开浏览器，处理退出 |
| [tile_explorer/engine.py](../../tile_explorer/engine.py) | 牌种目录、关卡参数、构造式生成、遮挡、取牌、工具、评分、状态导出与内部求解 |

| [tile_explorer/content.py](../../tile_explorer/content.py) | 三城主题、每城三条知识明信片、官方来源链接 |
| [tile_explorer/server.py](../../tile_explorer/server.py) | HTTP 适配、Cookie 会话、操作路由、静态白名单、完成记录读写 |
| [web/index.html](../../web/index.html) | 棋盘、上方候选槽、三个工具、知识卡、选关与规则弹窗的结构 |

正常操作链路为：浏览器点击 → `POST /api/action` → 服务定位会话 → `Game` 校验和修改状态 → 必要时记录通关 → 返回完整状态 → 浏览器重绘。前端不自行决定某张牌能否消除，也不乐观修改权威槽位。

启动器默认绑定 `127.0.0.1:8765`。默认端口绑定失败时尝试系统分配端口；显式设置其他非零端口失败时报告错误。`--port 0` 直接选择空闲端口，`--no-browser` 跳过自动打开网页。所有游玩素材位于项目内；知识卡来源链接在点击后访问外部页面，基础游玩无需联网。

## 3. 数据模型与状态

### 3.1 牌面与牌实例

`SYMBOLS` 是固定顺序的 18 项元组，水果、交通、宠物各六种。每项包含中文名称、颜色、稳定字符串 `code` 和类别。牌实例的 `kind` 是目录下标，`code` 用于前端图案映射。

`Tile` 是不可变数据类，字段为 `id、kind、x、y、z`：

- `id` 标识当前牌局中的牌实例；初始局使用从零开始的整数。
- `x、y` 是牌左上角世界坐标，每张牌的规则矩形为 `2 × 2` 世界单位。
- `z` 是层级。牌在槽中时仍保留原坐标，供单牌撤回恢复位置。

`Level` 记录关号、标题、城市、图案数、层数、路径压力、完整初始牌集合和一条合法通关路线 `solution`。

### 3.2 运行中的 Game

`Game` 主要维护三组数据：

1. **牌与槽**：`board` 按 ID 保存棋盘牌；`tray` 按实际展示顺序保存候选槽；`tray_order` 单独记录未消除牌的入槽先后，避免同类靠拢后丢失撤回顺序。
2. **规则与统计**：`status` 为 `playing、won、lost`；同时保存步数、消除组数、最高占槽、分数、总辅助次数和各工具次数。
3. **内部校验**：`certificate` 保存当前仍有效的构造通关路线，不作为界面提示输出。

`Game.state()` 导出棋盘牌的坐标、类型和 `blocked`；槽内牌只导出 ID 与类型。还包含关卡、主题、目录、剩余总量、工具可用性、统计、提示文本及通关星级。`remaining` 包含棋盘和槽中的所有未消除牌，已消除数由 `total - remaining` 计算。

服务端在此基础上附加共享的 `progress`，必要时附加 `save_warning`。该状态是展示快照，不是可直接恢复整个牌局的持久化格式。

## 4. 遮挡与普通取牌

`overlaps(a, b)` 以两个 `2 × 2` 矩形在 X、Y 方向都有正面积重叠为准；边缘相接不构成遮挡，比较中使用微小容差。`blockers()` 检查所有仍在棋盘中的牌，只将 `other.z > tile.z` 的相交牌计为挡牌。

因此，任意更高层都可以挡住下层，不局限于相邻层。同层不互相阻挡；几何生成器也禁止同层矩形重叠，使视觉与规则一致。

被压牌仍参与前端绘制，保留正常图案和亮度。普通点击只允许当前没有挡牌的实例；点击可见底牌时前端给出提示，服务端仍会独立校验。底牌“露出来可观察”与“允许普通取走”是两个条件。

## 5. 候选槽、三消及结算顺序

候选槽容量固定为七。`Game.pick()` 按以下顺序处理一次成功取牌：

1. 要求牌局仍在进行，ID 必须是整数且存在于棋盘；拒绝布尔值等伪整数。
2. 校验遮挡及是否为魔法笔取牌。魔法笔只接受被压牌，普通取牌只接受未被压牌。
3. 从棋盘移出牌；若槽内已有同类，插在最后一张同类后面，否则放在末尾；将 ID 追加到入槽顺序记录。
4. 步数加一，按此时槽长更新 `peak`。这里记录的是消除前占槽峰值。
5. 新牌使同类达到三张时，移除这三张及其入槽顺序记录，消除组数加一并加分。
6. 沿内部路线取牌时截去已完成的第一步；偏离路线则使原证书失效。
7. 棋盘和槽同时为空时判胜并加通关分；否则结算后槽长达到七时判负；其余情况继续。

第七张若构成三消，会先腾出空间，不能直接因入槽瞬间达到七而判负。即使该组三消成功，消除前峰值仍可被记为七。

### 5.1 分数和星级

每组三消得分为：

```text
100 + (7 - 本组三消后的槽内牌数) × 10
```

全部清空另加 `500` 分。当前没有时间、连击或音画组合加成。星级在通关时展示，计算为：

```text
1 + [peak ≤ 5] + [assists = 0]
```

方括号表示条件满足时加一。三个工具都会增加 `assists`；撤回不会倒退分数、已获消除组数、步数或占槽峰值。

## 6. 三个工具的具体实现

### 6.1 撤回

`undo()` 从 `tray_order` 末尾找到最近加入、仍在槽内的牌，将其从 `tray` 和顺序记录中移除，放回 `board` 原 ID 与原坐标位置。已三消的牌已从顺序记录中删除，因此不会被复原。

槽为空时拒绝撤回。槽不为空时可从满槽失败恢复为 `playing`；通关局槽为空，不能借撤回复活牌。撤回增加工具和辅助计数，清除原通关证书，其余累计统计保持。

### 6.2 魔法笔

前端的 `magicArmed` 只表示玩家是否点亮工具，不属于服务端牌局。点亮后点击被压牌，发送 `magic`；点击普通可取牌仍发送 `pick`。成功使用 `magic` 后关闭点亮状态，`Escape` 也可取消。

服务端 `magic(tile_id)` 调用 `pick(tile_id, penetrate=True)`，沿用同一套入槽、三消、计分与满槽结算，仅放行遮挡检查并增加魔法及辅助计数。未被压牌不能作为魔法笔目标。没有能量、次数或冷却限制。

### 6.3 整体重新排布

`shuffle()` 将棋盘和槽的所有未消除牌合并，生成新坐标、合法移除顺序及安全牌种序列，然后清空槽与入槽顺序，恢复 `playing`，生成新的通关证书。通关后禁止重排；满槽失败可以使用。

此操作保留剩余牌 ID 集合及每种图案的总数，但会沿新路线重新分配 ID 对应的 `kind`，不只是移动原牌位置。剩余图案计数仍是三的倍数，保证构造可以继续。随机种子由关号、累计步数和重排次数组合生成，因此相同操作历史可复现。

重排增加辅助次数，不重置分数、步数、消除组数或峰值；也没有三次上限。牌少时允许降低实际层数，避免少量牌挤成过深的小堆。

## 7. 九关生成与可解性

### 7.1 参数

| 关卡 | 城市 | 牌数 | 图案数 | 目标层数 | 路径压力 |
|---:|---|---:|---:|---:|---:|
| 1 | 巴黎 | 12 | 3 | 1 | 3 |
| 2 | 巴黎 | 18 | 4 | 2 | 3 |
| 3 | 巴黎 | 24 | 5 | 2 | 4 |
| 4 | 京都 | 27 | 6 | 3 | 4 |
| 5 | 京都 | 30 | 7 | 3 | 4 |
| 6 | 京都 | 33 | 8 | 3 | 5 |
| 7 | 纽约 | 36 | 9 | 3 | 5 |
| 8 | 纽约 | 42 | 10 | 4 | 6 |
| 9 | 纽约 | 48 | 12 | 4 | 6 |

`make_level()` 只接受整数 1–9，默认种子为 `20261019`，叠加关号偏移后创建独立随机数发生器。默认重开同一关产生相同初始局面。

### 7.2 先造路线，再填图案

生成过程依次为：

1. 通过 `make_positions()` 生成满足露出要求的坐标。
2. `removal_order()` 根据遮挡关系，在当前可取牌中随机选择，获得一条清空几何布局的合法顺序。
3. 从水果、交通、宠物交错的牌种序列中按城市偏移选择本关牌种；以组三张方式填充 `Counter`，保证各牌种总量都是三的倍数。
4. `safe_kind_order()` 构造槽位占用受控的牌种序列，并将其按合法移除顺序填到牌实例上。
5. 保存该移除顺序为 `Level.solution`，供内部回放校验。

`pressure` 约束构造路线的消除后槽位占用，并为完成已有组保留空间。它是生成参数，不等于真人体验难度。权重倾向于引入或延续未完成组，使路线不全是连续三张直接消除。

### 7.3 保证的边界

初始局和重排局至少存在一条构造路线。玩家沿证书取牌时，保留证书剩余部分；改取其他牌或撤回会清除原证书，但不据此判定玩家已无解。当前没有每步自动兜底，也不保证任意取法都能通关。

`find_solution()` 是内部有限搜索工具，支持已有槽的局面，以剩余牌位图、挡牌位图和槽内各类计数进行记忆搜索，优先尝试完成已有组。默认上限为 18,000 个节点和约 0.22 秒；返回 `None` 既可能表示找不到解，也可能是预算耗尽，不能视为严格无解证明。它不是前端提示功能。

## 8. 紧密交错几何与露出保证

[geometry.py](../../tile_explorer/geometry.py) 在半世界单位网格上计算。每张 `2 × 2` 牌占 `4 × 4`、共 16 个离散格子。放置上层牌时，从被其覆盖的下层牌可见格子中减去上层占格，并要求每张受影响牌同时满足：

- 至少剩四格，即牌面矩形面积的四分之一。
- 剩余格中包含连续的 `2 × 2` 网格块，即完整的一世界单位方形区域。

这里保证矩形牌面的真实露出面积，图案具体像素的辨认效果还取决于图集和缩放。浏览器露出区命中检查属于另外的历史实测。

底层以五列连通地毯为主，中央预留空洞，只裁去外角。上层候选牌不得进入中央空洞；同层不得重叠；每张上层牌至少跨住两张下层牌，其中至少一张位于紧邻下层。这样形成跨牌叠压，避免独立斜向小堆。

九关使用显式层数分配，例如第九关四层为 `32 / 9 / 5 / 2`。剩余局面使用通用分配；少量剩余牌可退为平铺。每个层数方案有八次随机尝试和四套固定种子回退；仍失败则减少层数，最后平铺。生成过程有有限边界，不会无休止寻找布局。最终可随机镜像并打乱位置列表，改变视觉顺序而保留几何性质。

## 9. 前端图集、布局和交互

### 9.1 牌面与主题

牌面使用本地 [tile-atlas-v3.png](../../web/assets/tile-atlas-v3.png)，真实尺寸 `1774 × 887`，透明背景，按六列三行排列。CSS 以 `background-size: 600% 300%` 截取；`atlasPositions` 根据各图透明边界单独校准中心，再统一放大 `1.42` 倍以裁去留白。原 PNG 不在运行时修改。图集与牌种的顺序映射、制作记录见 [ASSETS_V3.md](../ASSETS_V3.md)。

`Image.onload` 成功后添加 `tile-art-ready`，启用图集并隐藏内联 SVG 图案。加载未完成或失败时仍有本地 SVG 后备图案。厚牌边框和阴影由 CSS 绘制，图集本身不包含牌框。底牌没有额外变暗或重复角标。

城市背景由 `sceneSvg()` 生成本地内联 SVG；`sceneKey` 避免每次操作重复替换背景。`content.py` 提供每关知识和来源，前端按城市和章节更新配色、标题、明信片和旅行进度。来源只允许 HTTPS 链接写入 `href`。

### 9.2 世界坐标映射

棋盘牌按层、Y、X 和 ID 排序绘制，`z-index = z × 100 + 1`，保持高层覆盖低层。浏览器按钮矩形负责实际命中，图案和装饰不拦截指针。

`layoutBoard()` 按棋盘宽度和整体世界坐标边界计算等比缩放，并限制每世界单位最大 42 像素；牌宽高约为 `2 × scale - 1`，留出边界。棋盘高度在约 300–620 像素间随布局和视口调整，小屏上限为 600 像素。

首次布局缓存 `boardBounds`。普通取牌、撤回沿用该参考框，防止剩余牌不断重新居中；选关、重开、下一关和重排后清空边界重新计算。`ResizeObserver` 配合 `requestAnimationFrame` 处理视口变化。

### 9.3 重绘、请求和基本可访问性

当前 `renderBoard()`、`renderTray()` 都会全量替换子节点，每次响应直接展示最终状态；没有按牌 ID 保留角色动画，也没有入槽/三消中间表现事件。七格槽由 CSS Grid 绘制，槽内六张起改变底色，五张起计数提示危险。

`busy` 在等待请求期间阻止重复提交；请求成功后更新 `state` 并重绘，业务错误若携带权威 `state` 也会同步。连接错误展示本地服务提示，初始化失败允许点击棋盘重试。

牌按钮和槽位带有中文 `aria-label`，工具使用禁用状态，魔法笔使用 `aria-pressed`。`Z` 撤回、`Escape` 收起魔法笔；输入控件、弹窗打开或修饰键按下时跳过相关快捷键。CSS 已对 `prefers-reduced-motion` 关闭基础过渡，但此版没有音效管理和小剧场动画系统。

## 10. HTTP 接口与会话

### 10.1 接口

| 接口或动作 | 行为 |
|---|---|
| `GET /api/state` | 定位或创建会话，返回完整状态 |
| `POST /api/action`，`pick` / `magic` | 接受 `tile_id`，执行普通或穿透取牌 |
| `undo` / `shuffle` | 执行单牌撤回或剩余牌整体重排 |
| `restart` | 用当前关号创建新 `Game` |
| `level` | 接受 `level`，自由选择 1–9 关并新建牌局 |
| `next` | 当前必须已通关且小于第九关，再创建下一关 |

成功返回 HTTP 200 和完整状态。规则错误返回 400，包含 `error` 与当前 `state`；格式错误只有错误说明。未知静态路径或接口为 404，本地 Host/外部 Origin 不符合约定时为 403，白名单资源读取失败为 503。第九关没有第十关，界面转为重访选关。

### 10.2 会话与并发

`GameServer` 使用 `ThreadingHTTPServer`，通过一个 `RLock` 串行访问会话、牌局和完成记录。随机 `tile_session` Cookie 以 `secrets.token_urlsafe(24)` 生成，设置 `HttpOnly、SameSite=Strict、Path=/`。

Cookie 对应的 `Game` 仅保存在服务内存中。同源且共享 Cookie 的标签页会访问同一局；不同 Cookie 会话隔离。刷新可继续，服务重启后内存局面丢失。会话上限为 128，新增时若超限移除最早插入的会话；当前没有超时清理或磁盘牌局恢复。

### 10.3 本机服务边界

启动入口只绑定回环地址。请求 `Host` 必须是实际端口上的 `127.0.0.1` 或 `localhost`；POST 若存在 `Origin`，也必须匹配对应本机地址，无 Origin 的本机请求可接受。

请求体要求正长度且不超过 16,384 字节，并且是合法 UTF-8 JSON 对象。静态内容使用明确白名单，只暴露主页、JS、CSS 和当前图集，不将整个项目目录公开。

响应附加 `Cache-Control: no-store`、`X-Content-Type-Options: nosniff` 和 CSP：默认资源同源；脚本和连接同源；图片允许同源及 data；样式允许同源及内联；禁止被其他页面嵌入。该结构服务于本机原型，不包含账号、云端同步或公网发布能力。

## 11. 完成记录与写盘容错

存档文件固定为项目 `.local/travel-progress-v2.json`，新版使用 `completed` 区段，例如：

```json
{
  "completed": {
    "1": {"stars": 3, "best_score": 1180}
  }
}
```

示例数字仅解释格式。记录在本地服务实例内由所有会话共享，不按 Cookie 分别保存。每关最高星级与最高分分别取历史最大值，二者可能来自不同通关局。

只有操作完成后状态为 `won` 才调用 `Progress.record()`；重开、选关不删除已完成记录。该文件不保存棋盘、槽、当前关或操作历史，也不使用浏览器 localStorage 保存局面。旧的其他分区不会迁移到本版完成记录。

读取时仅接受 1–9 关、1–3 的整数星级和 0–1,000,000 的整数分数，跳过无效记录；文件缺失视为空进度，损坏或无法读取则保留可启动状态并提供警告。

写盘先更新内存，再写同目录 `.tmp` 文件并替换目标文件。失败时保留内存记录、设置 `dirty` 和提示；下次调用记录函数时，即使最高分未变也会重试。此行为没有后台定时重试或多进程存档协调。
