# v0.5 技术方案：滑动让路，碰撞合成

方案、实施与部署日期：2026-10-23。状态：**已在 `v0.5` 分支实现，本地、预览及公网验证通过，已部署**。第 1–13 节保留原方案及设计模型边界，实施与发布记录见第 14–15 节。

基于当前 v0.4 分支 `codex/v0.4-first-three-polish`，本次核对的提交为 `e39cdc4`。本文件规定下一轮原型的规则、三关草案、输入、架构、验关和验收方式；参数和布局允许根据试玩调整。文中明确标注的“设计模型验证”是独立数学模型的计算结果，不是生产内核或浏览器验收结果。

## 1. 本版要验证什么

玩家在单层棋盘里，上下左右滑动一块方块，让出通路，再让相同方块碰撞合成。合成目标自动收集，腾出的空间用于下一次操作。

本版的体验问题是：**玩家是否会自然地想到“先把旁边这块挪开”，并从挪开、凑对、腾出空间的连续操作里获得乐趣？**

当前拖拽的主要决策是寻找合法配对；暂放位常用于解除特定遮挡。滑动版本把操作空间放回棋盘，让路成为常规动作。借用华容道的空间关系，但保持小棋盘、少种类、短距离；前三关不要求长距离搬运或记住多步解法。

| 内容 | v0.5 首轮决定 |
|---|---|
| 棋盘 | 单层、矩形、等尺寸格子，图案全部可见 |
| 主操作 | 在一块方块上划动，一次只沿一个方向移动一格 |
| 合成 | 主动滑向紧邻的同类方块，消耗两块，完成一个对应目标 |
| 操作空间 | 棋盘上的空格；移除暂放位 |
| 目标 | 收齐本关指定成品，并清空基础方块 |
| 内容 | 复用草莓、汽车、树苗及各自成品，共六张图形 |
| 难度 | 先滑动，再让路，再选择更顺手的让路方向 |
| 失败压力 | 无时间限制、无步数上限、无星级扣分；保留撤销和重开 |
| 首轮规模 | 三关可玩原型，先确认基本操作是否成立 |

首轮不加入整体滑盘、斜向移动、交换、推一整排、惯性弹球、自动落下、多级合成或随机补牌。此前“上层相邻交换”和“合成后沿轨道补位”属于不同候选方向，本版不混入。

## 2. 规则合同

### 2.1 空间与移动

每块占据一个格子。规则坐标使用整数 `row/col`，从 0 开始；文档里的关卡解法从第 1 行、第 1 列开始计数。方块没有上下层、遮挡比例或连续世界坐标。

一次动作只检查源格相邻的一个目标格：

| 目标情况 | 结果 | 操作数／历史 |
|---|---|---|
| 棋盘内空格 | 方块移动一格，源格变空 | 加 1／可撤销 |
| 相同基础图形 | 消耗源、目标两块，交付对应成品 | 加 1／作为完整事务撤销 |
| 不同图形 | 被挡住，短促抵住反馈 | 不增加／不写历史 |
| 棋盘外 | 被边缘挡住 | 不增加／不写历史 |
| 轻点、距离不足或取消手势 | 无动作 | 不增加／不写历史 |

不跨越方块，不隔空配对，不将被撞方块向后推。长划动在首轮仍然只走一格，连续两格需要两次手势；这是初始手感假设，必须观察玩家是否觉得重复划动繁琐。

### 2.2 合成、交付与胜利

- 草莓 + 草莓 → 大草莓；汽车 + 汽车 → 跑车；树苗 + 树苗 → 大树。
- “相同”依据内容注册表中的 `itemId` 和配方判断，不依据颜色或显示名称。
- 相邻的同类可以稳定共存。只有主动向同类滑动才触发合成；启动、刷新、撤销或结束动画都不会自动消除相邻方块。
- 一次手势最多产生一次合成，无连锁扫描。
- 成品短暂出现在碰撞格并飞向对应目标；它只是表现对象，不是可以继续移动或合成的规则实体。
- 规则提交时两格立即变空、对应 `delivered[resultId]` 加 1。目标计数与实际状态一致，动画不负责延迟增加计数。
- 完成条件是所有目标数量精确满足，且棋盘为空。不能只比较目标总数。
- 首轮每种基础材料数量必须等于对应目标数量的两倍，不添加无法使用的“干扰牌”。

合成增加两个空格；普通移动只改变空格位置。后半局逐渐宽松是本版允许的节奏，先观察是否产生清理完成的爽感，再决定是否需要其他变化。

### 2.3 “能动”“有解”“好玩”分开判断

能滑动不代表能完成目标。一个局面可能来回移动但没有通关路线，不能用“合法操作数量大于零”代替可解性判断。

本版发布要求高于“开局至少有一条解”：前三关在全部合法可达局面中，都应当还能通关。撤销帮助玩家试错，不承担补救必然死局的职责。

此外，两对已经能直接合成的牌，先后消除通常得到相同局面。**不把这种等价顺序当成策略深度。** 首轮的小技巧来自让路方向和移动后的配对位置。

## 3. 三关草案与具体解法

符号：`S` 为小草莓，`C` 为普通小车，`T` 为小树苗，`.` 为可进入的空格。图示中的空格都是真实棋盘格，格子之间的装饰间隙不是落点。正式游戏使用现有图形，不显示这些字母。

前三关分别使用 2 行 × 3 列、2 行 × 3 列、3 行 × 3 列。第一关有意留得宽松，只教操作；第二、三关分别有 2、3 个初始空格。棋盘外的背景不能放牌。

### 3.1 第一关：滑过去，碰一下

```text
S . S
. . .
```

目标：大草莓 × 1。参考解法：

1. `(1,1)` 的草莓向右，进入 `(1,2)` 空格。
2. 同一草莓再向右，碰到 `(1,3)` 草莓，完成合成与收集。

左右对称的路线也成立。玩家向下绕路仍能继续完成，教程必须跟随实际局面，不强迫回到参考步骤。

教学重点是“在一块上滑动”“一滑一格”“碰到同类才合成”。第一次移动后，旁边的同类不自动消失，让玩家亲手完成第二次划动。

### 3.2 第二关：让个位置

```text
S C S
C . .
```

目标：大草莓 × 1、跑车 × 1。参考解法：

1. `(1,2)` 的汽车向下，进入 `(2,2)`，给上排让路。
2. `(1,1)` 的草莓向右至 `(1,2)`。
3. 同一草莓再向右合成，自动收集大草莓。
4. `(2,1)` 的汽车向右，与 `(2,2)` 汽车合成。

第一步之后也可以立即合成下排汽车，再处理草莓，两条路线都接受。玩家发现“挡路的汽车挪一下，也凑成了一对”。

### 3.3 第三关：往哪边挪，更顺手

```text
S C S
C T .
T . .
```

目标：大草莓 × 1、跑车 × 1、大树 × 1。参考解法：

1. `(2,2)` 的树苗向下至 `(3,2)`。
2. `(3,1)` 的树苗向右合成大树，清空中心和底排。
3. `(1,2)` 的汽车向下至 `(2,2)`。
4. `(2,1)` 的汽车向右合成跑车。
5. `(1,1)` 的草莓向右至 `(1,2)`。
6. 同一草莓继续向右合成大草莓。

也可以先把中心树苗向右挪到 `(2,3)`。它同样给汽车让了路，但树苗彼此变远，最优后续需要总共 8 步完成，而向下开局只需 6 步。两种都能过关，不给前一种打叉，也不要求玩家一开始算出最短路线。

想让上排草莓立刻相碰需要较长准备；界面不把草莓指定为必须先完成的目标。玩家可以先看到眼前的树苗配对，再逐步打开汽车和草莓，这是本关降低规划负担的关键。

### 3.4 本次已经执行的设计模型验证

对上述草案使用独立离散模型，按“单块移动一格、同类碰撞消耗双方、无补牌”的规则，完整枚举可达局面，再从胜利局面逆向标记可通关状态。

| 关卡 | 初始方块／空格 | 最短有效操作 | 不同可达局面 | 无法通关的可达局面 |
|---|---|---|---|---|
| `slide-01` | 2／4 | 2 | 16 | 0 |
| `slide-02` | 4／2 | 4 | 121 | 0 |
| `slide-03` | 6／3 | 6 | 9,937 | 0 |

原始布局、参考路线、第一步分支和模型边界记录在 [v0.5-layout-study.json](v0.5-layout-study.json)。同类方块在规则上完全等价，因此模型按图形而非实体 ID 合并局面；已交付数量由初始数量与剩余数量确定。

**这些数字只证明三份草案在该设计模型下的性质，不证明游戏已经实现或有趣。** 正式实现必须用真实 `slide-v05-1` 内核重复完整验关；若规则或布局变化，重新计算，不能照抄此表作为验收记录。

## 4. 滑动输入与连续操作

### 4.1 手势识别

统一鼠标、触摸和触控笔到 Pointer Events，只维护一条主指针手势。按下时记录 `tileId`、起点、棋盘变换、`revision` 和本轮生命周期令牌。

初始手感参数集中放在 `settings.js`，均为待试玩校准值：

| 参数 | 初始值／规则 |
|---|---|
| 开始识别方向 | 屏幕位移超过 8 CSS px |
| 锁定横／纵轴 | 较大轴位移至少是另一轴的 1.35 倍 |
| 有效释放距离 | `clamp(格子屏幕宽度 × 0.18, 12, 24)` CSS px |
| 单次移动上限 | 一格；不按距离累计动作 |
| 普通落位 | 约 100–140 ms |
| 被阻挡的位移反馈 | 沿操作方向最多约 6 CSS px，再回位 |
| 成品出现与收集 | 约 250–400 ms，可打断，不锁输入 |

方向未明确时，不提前猜测斜向意图。方向锁定后只沿该方向预览；移回起点附近或反向越过起点，松手取消本次动作。下一次手势可以换方向。

`pointerup` 必须使用释放瞬间的坐标重新计算，即使期间没有收到 `pointermove` 也能正确识别。轻点只给选中／焦点反馈，不提交动作。

目标只有相邻格，不使用旧版“寻找最近底牌”的吸附算法。选中时预览可走空格或可合成对象；不同牌或边缘以局部抵住反馈说明阻挡，不反复弹错误框。

### 4.2 动作提交与表现分离

1. 输入控制器生成 `{type: 'slide', tileId, direction}` 意图。
2. 会话核对当前版本与生命周期，用内核验证相邻格。
3. 成功后一次性更新局面、目标、历史和保存数据。
4. 当前原生事件结束后，在下一帧同步节点并启动表现。
5. 新手势可以打断已有落位或收集效果；以最新稳定状态为准，不等待整段动画。

提交后，下一次按下先结束受影响节点的旧过渡，让节点位置和命中区域与规则状态一致。成品和残影 `pointer-events: none`，不能挡住新空格或误收第二次目标。

窗口变化、页面隐藏、弹窗、撤销、重开和切关都会取消未提交手势、教程提示与旧动画。旧回调必须核对令牌，不得在新局面里“补一次移动”。忽略第二根手指；`pointercancel` 不产生动作。

棋盘设置 `touch-action: none`，范围不扩展到整个页面。指针捕获保证手指离开牌面仍能完成同一手势。页面尺寸变化时取消手势并重算格子尺寸，不混用旧坐标。

### 4.3 键盘和可访问操作

- Tab 聚焦存活方块；方向键向对应方向移动一格。
- 按住方向键的自动重复事件首轮忽略，避免一次长按连走数步；再次按键才是新动作。
- `Ctrl/⌘ + Z` 撤销，Esc 关闭弹窗或取消当前预览。
- 方块的可读名称包含图形、行列。合成后焦点移到附近仍存在的方块；通关后移到“下一关”。
- 目标更新用简短状态播报；颜色之外还用目标轮廓、箭头和形状传达反馈。

## 5. 界面、图形与教学

### 5.1 布局

沿用暖黄背景、厚白方块、紧凑顶栏与底部工具的视觉基础。棋盘改为可辨认的凹槽格，空格与棋盘外背景有明显区分；方块不再有“浮在另一块上”的视觉层级。

- 顶部：关卡、设置入口，目标栏按成品图形分别展示进度。
- 中间：固定棋盘，合成后保留全部格子，不因方块变少而居中重排。
- 底部：撤销、重开、怎么玩；成功后提供下一关。
- 移除暂放位、上层／底牌说明、拿起再放下的键盘说明。
- 游戏显示名暂用“滑出新花样”；统一修改页面标题、简介、选关、帮助、状态文案与读屏标签。
- 操作数不是倒计时或失败条件，可弱化显示；先不加最优步数、三星或效率排名。

三列棋盘用统一格子尺寸，格间距初始约 6–8 CSS px，视口缩放时整体调整。避免把空白背景做成额外“暂存区”。320 px 宽度下方块操作区域不少于 56 × 56 CSS px，工具按钮不少于 44 × 44 CSS px；短屏允许页面适度滚动，棋盘内部不随手势滚动。

### 5.2 内容与素材

复用 `web/assets/merge-v04/` 内六张 SVG 和现有合成音效，不因版本号改变复制一份素材。配方显示为“两个小图形 → 成品”，只展示本关会用到的种类。

移动是轻短滑行，合成在碰撞格给出一次明确成长反馈，再收集到正确的目标图形。草莓、汽车、树苗的既有效果可复用；音效关闭、资源失败或减少动态效果都不影响规则执行。

此轮不生成新素材，也不扩成长升级链，先让图形服务于辨认与配对。

### 5.3 非阻塞教学

| 阶段 | 展示什么 | 学会的判定 |
|---|---|---|
| 第一关初次接触 | 方块上的短方向箭头和手势虚影：“向旁边滑一格” | 实际完成一次进入空格的移动 |
| 第一次配对机会 | 对同类方向的短预览：“碰到相同图案，会合成” | 实际完成一次合成与交付 |
| 第二关 | 必要时点亮挡路方块旁的空格：“挪一挪，给它让路” | 在该关发生有效让路操作后继续配对 |
| 第三关 | 默认自主尝试；帮助入口可请求当前一步 | 不强制执行预设路线 |

沿用虚影不拦输入、真实操作立即取消、演示限轮次的原则。初始延时约 600 ms，闲置提示约 4 秒；实际值放在配置中。玩家采用其他合法路线时，重新根据当前局面选择提示，不继续播放旧坐标的动画。

能力记录依据成功动作，不依据看过提示或滑动次数。帮助只读，不替玩家走棋。“重看指引”不重置牌局。普通弹窗关闭后恢复当前适用的指引。连续无效输入也只能给局部、简短建议，不能整屏强制接管。

## 6. 工程结构与当前代码接入

### 6.1 技术选择

继续使用原生 JavaScript、DOM/CSS 和已有 Python 本地启动器，发布为纯静态 H5。当前只有最多 9 个格子，不需要物理引擎、服务端规则或更换为 Phaser。棋盘依然采用纯规则状态驱动节点，浏览器表现不反向决定游戏事实。

v0.4 与新规则的层叠、遮挡、暂放和输入语义差别很大，新增独立 `slide-v05` 模式；保留 v0.4 对照入口，避免用大量 `if (v05)` 改造旧内核。也不复制旧模式的全部文件后仅改名称。

原方案建议分支名为 `codex/v0.5-slide-merge`；实施时按用户明确要求，实际创建 `v0.5`，基于 v0.4 的 `e39cdc4` 开始开发。

### 6.2 拟新增模块

## 7. 数据模型与事务

### 7.1 关卡定义

拟定规则版本 `slide-v05-1`。例：

```js
{
  id: 'slide-02',
  ruleset: 'slide-v05-1',
  rows: 2,
  cols: 3,
  tiles: [
    {id: 's1', itemId: 'strawberry-small', row: 0, col: 0},
    {id: 'c1', itemId: 'car-small',        row: 0, col: 1},
    {id: 's2', itemId: 'strawberry-small', row: 0, col: 2},
    {id: 'c2', itemId: 'car-small',        row: 1, col: 0}
  ],
  goals: {'strawberry-large': 1, 'sports-car': 1},
  goalOrder: ['strawberry-large', 'sports-car'],
  tutorialId: 'make-room',
  referenceSolution: [
    {type: 'slide', tileId: 'c1', direction: 'down'},
    {type: 'slide', tileId: 's1', direction: 'right'},
    {type: 'slide', tileId: 's1', direction: 'right'},
    {type: 'slide', tileId: 'c2', direction: 'right'}
  ]
}
```

定义校验拒绝：越界、重格、重复 ID、未知基础图形、非整数尺寸／目标、无配方、材料与目标不匹配、成品出现在初始棋盘、非法参考动作。前三关至少有一个空格；不支持障碍格或非矩形洞口。

定义哈希涵盖规则版本、行列、实体 ID／图形／位置、目标与实际配方输入输出。标题、说明、动画时长、参考解顺序和素材 URL 不改变规则身份。

### 7.2 稳定状态与命令

稳定状态包含：关卡身份、定义哈希、行列、存活 `tiles`、目标、已交付计数、有效操作数及状态。位置只存一份 `row/col`；占用表由状态推导或作为内核内部缓存，界面不能维护另一份事实来源。

核心接口拟为：

```js
createState(level)
inspectAction(state, action)   // 只读返回 move / merge / blocked 及目标格
applyAction(state, action)     // {ok, state, transaction, events} 或拒绝原因
listLegalActions(state)
replay(level, actions)
canonicalKey(state)
validateLevel(level, budget)
```

内核不依赖 DOM、时钟、音效或 localStorage。输入带来的 `expectedRevision` 在会话入口校验，不成为持久化规则动作的一部分。

成功事务包括完整动作、前后稳定状态和事件；普通移动产生 `tile-moved`，合成产生带源／目标 ID、碰撞格、`recipeId/resultId` 的 `merged-and-delivered`，最后一步还产生 `level-completed`。小棋盘先用完整快照保证撤销可靠，不先做复杂增量压缩。

撤销恢复两块牌、位置、目标计数和操作数，是一次整体恢复；会话 `revision` 仍单调递增，不能回到旧 revision 导致陈旧手势重新有效。重开／切关另增生命周期令牌。

## 8. 正式可解性验证与提示

### 8.1 为什么不能沿用旧的递归判断

普通滑动可以往返，所以状态图有环。递归遇到“正在访问”的状态时直接记死局，会误判；统计全部操作序列的“解法总数”也可能因循环而无穷大。

正式验证采用有限状态图方法：

1. 通过实际 `engine.listLegalActions/applyAction` 从开局广度搜索，记录不同局面和有向边。
2. 规范化键包含行列、逐格图形、完整目标与交付计数、规则／定义身份。动作数、revision、动画状态不参与键。
3. 同图形、同阶段方块没有个体规则属性，可以忽略实体 ID 合并等价状态；如果以后引入耐久、锁定或个性能力，必须扩充键。
4. 从所有胜利状态沿反向边广度搜索，得到可通关集合和到胜利的最短距离。
5. `全部可达集合 - 可通关集合` 是无法通关的局面，包括没有出路的循环区域。
6. 三关必须初始可解且该差集为空，参考解全部合法，并与正式内核生成的目标结果一致。

报告记录定义哈希、规则版本、搜索是否完整、不同状态数、动作边数、最短距离、不可通关状态和必要的反例路线。边数可以包含不同合法方向带来的同一个后继；“不同状态数”按规范化键去重，定义需在报告中注明。

### 8.2 搜索预算和运行时提示

离线验证初始预算可设为每关 100,000 个不同状态，耗尽或异常返回 `unverified` 并使发布检查失败；不能把“没搜完”写成通过，也不能误称无解。根据正式实现的实测耗时再定时间预算。

帮助中的“一步提示”根据当前状态求一条有效通关路线，只显示第一步。搜索使用相同纯内核和规范化规则；按约 4 ms 的小时间片让出主线程，并缓存同关已算结果，不在每次指针移动时搜索。初始总预算约 1 秒，超过预算显示“暂时没找到提示”，不阻断继续操作，也不把它当死局。

所有异步结果检查关卡、定义哈希、revision 与生命周期令牌；局面变化即丢弃旧结果。搜索执行到完整结束才能报告无解。提示缓存不保存界面节点。

### 8.3 后续关卡生产

首轮人工制作小布局并完整验关。以后可以从已知解倒推布局，再用正向实际内核验证；生成时只允许合法逆移动，逆合成也必须对应“相邻同类碰撞”的正向动作，不能随便拆到远处。

一条参考解只能证明开局可解，不能替代全可达验证。扩大棋盘造成搜索超预算时，先缩小设计空间或改进验证，不默默降低前三关的无死局承诺。批量扩展 50 关放在玩法成立之后。

## 9. 存档、历史与兼容

使用独立存档前缀 `tile-explorer.slide.v05.`，预览使用 `tile-explorer.slide.v05.preview.`。关卡进度、教程能力、进行中会话和设置分别存储；同源的新旧版不会共享牌局。

进行中会话记录 `schemaVersion`、`ruleset`、`levelId`、`definitionHash` 与有效操作序列。恢复时从关卡开局用真实内核逐步回放，重建稳定状态与撤销历史；格式、规则、材料或动作校验失败则安全重开该关，并用简短文案说明。

**必须去掉旧版 `moves.length <= 2 * totalGoals` 的限制。** 滑动有往返操作，合法动作数不再由材料数限定。至少验收连续 300 次合法往返后继续合成、保存和刷新恢复。

首轮保持完整动作日志，不把任意中途快照当成已验证存档。读取设置防止损坏数据占用过多资源的技术上限：初始为 2 MiB 文本及 50,000 条动作，回放分时间片执行。该上限不是关卡步数限制；若当前局面无法持久化，游戏继续以内存状态运行，并提示刷新可能丢失进度，不能悄悄截断动作后保存成错误局面。阈值在正式实现性能测试后校准。

仅继承 v0.4 设置中通过类型校验的音效和减少动态效果偏好，不迁移关卡完成记录或已学会的“暂放”教程。旧键原样保留。HTTP 与 HTTPS 是不同存储来源，不承诺协议切换后进度自动互通。

撤销和重开取消旧成品动画；撤销胜利动作恢复为可继续操作状态。已经取得的关卡完成标记可以保留，当前局面仍以回放结果为准。

## 12. 验收计划

### 12.1 规则与回归

- 空格移动、同类碰撞、异类阻挡、边界、非法方向、未知实体和陈旧动作。
- 相邻同类不自动合成；长手势最多一次动作；无意外连锁或成品实体。
- 普通移动保持材料总量，合成恰好少两块并交付一件对应成品。
- 所有状态每格最多一块，目标不超量，胜利必须全部目标满足且棋盘空。
- 参考解可回放；逐次撤销回到精确开局；重开、恢复后的后续结果与新运行一致。
- 正式验关具有循环案例、不可通关循环案例、搜索超预算案例，防止把有环或未搜完误判为成功。
- 新规则含同类实体的对称局面，验证规范化不改变可行动作与可解性。
- 旧模式内容注册表抽取、资源清单、服务白名单与导出兼容通过原有检查。

### 12.2 浏览器与设备

以真实事件通过新三关，覆盖鼠标、原生触摸事件模拟和键盘。重点验证：快速滑动、慢滑回撤、斜滑、只收到按下／释放、越出牌面、多指、连划、撤销打断合成、切关时释放、页面隐藏和窗口缩放。

至少覆盖 320×568、375×667、390×844、768×1024、1440×900 五种视口；检查棋盘全部可见或可正常滚动到达、目标和工具不遮住方块、空格与背景容易分辨。检查主入口和独立静态包，控制台没有未处理错误，资源没有缺失。

存档测试包括超过旧操作上限、300 次往返、混合材料进度恢复、无效数据、存储被禁、旧版隔离和预览隔离。静音／减少动态效果下仍能辨认合法移动与成功合成。

性能要求首先是无动画等待、无重复提交、无节点错位。搜索、存档回放及动画的实际耗时需在报告中记录设备和浏览器，不能用未实测的“60 FPS”作结论。模拟触摸通过不等于 Android/iOS 真机通过；真机没有条件时明确列为未完成。

### 12.3 玩家体验试验

先找至少 5 位未参与设计的人做小样本观察，不提前讲解解法。初始判断标准：

| 观察项 | 首轮判断目标 |
|---|---|
| 第一关操作理解 | 至少 4 人能靠界面指引完成首关，无需旁人口头指导 |
| 第二关主动让路 | 至少 3 人在未请求“一步提示”时尝试移动挡路汽车或建立另一条合法路线 |
| 第三关选择 | 记录树苗向下、向右等实际选择及后续困惑；不要求选中最短解 |
| 操作负担 | 记录连续重划、误认长划多格、反复点空格、把整盘当成整体滑动的情况 |
| 合成预期 | 不应反复等待相邻牌自动消除，也不应寻找第二件成品继续合成 |
| 主观感受 | 让玩家描述最舒服和最烦的一次操作，判断是否只是增加了搬运步骤 |

这些是原型筛选标准，样本小，不用于宣称留存率或“上瘾”。若有多人持续认为划动繁琐，先调整一格手势或缩短有效路径；若完全不用考虑让路就能完成，调整空位和布局，而不是优先增加规则。
